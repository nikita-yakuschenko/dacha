# Задание для Codex: сайт «Просто Дача»

Ты — опытный frontend-разработчик и product/design engineer. Создай полностью работающий, аккуратный, адаптивный коммерческий сайт «Просто Дача» на **Next.js (App Router) + TypeScript + Tailwind CSS + shadcn/ui**. Работай непосредственно с файлами проекта, запускай и проверяй результат. Делай полноценную реализацию, а не презентацию или набор картинок.

## Главный принцип: «Просто» — продуктовая и UX-концепция

Простота должна чувствоваться во всём: в геометрии, композиции, навигации, выборе дома, характеристиках, формулировках, заявках и мобильных взаимодействиях. Сайт должен выглядеть современно, спокойно, эстетично и убедительно, без перегруза. Это не шаблонный строительный сайт и не перегруженный luxury-лендинг.

**Ассортимент строго ограничен дачными / садовыми домами.** Никаких беседок, бань, гаражей, хозблоков, навесов, мобильных бань и малых архитектурных форм — ни в каталоге, ни в CTA, ни в навигации, ни в FAQ. Базовое предложение — сезонные дома из одинарного мини-бруса; не называть их безусловно пригодными для зимнего проживания.

## 1. Источники проекта и как с ними работать

Папка пакета:
- `source/minibrus-landing-brief.md` — **основной источник продуктовой логики, ограничений и текстов**; прочитать целиком.
- `source/minibrus-landing-concept.zip` и `source/minibrus-landing-concept (2).zip` — архивы старых рабочих прототипов/сопроводительной документации; распаковать и сравнить. При совпадениях не дублировать компоненты.
- `source/minibrus-garden-houses-standalone.html` — предыдущий интерактивный прототип: использовать как референс сценариев и содержимого, НЕ как эталон визуала или код для дословного переноса.
- `references/visual-concepts/01-hero-desktop.png` … `09-faq-and-final-cta-desktop.png` — **визуальные концепты**, их композиционный язык: тёплый ivory, насыщенный зелёный, крупная типографика, значимые фото и минимум визуального шума.
- `references/logo/` — утверждённое направление логотипа и векторизованные SVG. Использовать SVG с контурами букв; **запрещено набирать название другим шрифтом и имитировать знак через CSS**. Не изменять геометрию, расстояния и характер линий.

Скриншоты — **не готовый дизайн для копирования pixel-perfect**. У них есть генеративные ошибки: неподтверждённые цены (например 1 290 000 ₽), случайные спецификации, обещания доставки «по всей России», «монтаж 1–3 дня», гарантии, фиктивные отзывы, контакты, название населённых пунктов/адреса, иногда несоответствия планов и размеров. **Не переносить эти заявления как факты!** Использовать только дизайн-язык и разумные UX-идеи, проверяя каждое утверждение по Markdown-брифу.

Реальные фотографии/визуализации отсутствуют в этих материалах. Скриншоты макетов нельзя нарезать и выдавать за фотографии построенных объектов. Можно временно использовать целые референсы в отдельном режиме `concept-preview`, а для рабочего сайта — честные локальные заглушки с правильными пропорциями, явной пометкой «Концептуальная визуализация» и простой процедурой замены на утверждённые изображения. Не забирать фото конкурентов.

## 2. Технологический стек

- Next.js актуальной стабильной версии, **App Router**, TypeScript strict, React, Server Components по умолчанию.
- Tailwind CSS (актуальная совместимая версия), **shadcn/ui** (именно компоненты с локальным контролируемым кодом), Radix primitives по необходимости.
- Icons: **Tabler Icons** — лёгкие монохромные, единая толщина линий; никаких смешанных наборов.
- Шрифты: Inter / Inter Display (или легально доступный очень близкий нейтральный гротеск) для интерфейса, заголовков и маркетинговой типографики. Но написание **в логотипе остаётся в SVG-контурах**, не воспроизводится шрифтом.
- Используй `next/image`, responsive `sizes`, оптимизированные локальные изображения, `next/font` если доступно; не создавать тяжёлый client-side bundle без необходимости.
- Формы: React Hook Form + Zod (при необходимости), валидация и доступные состояния. UI компоненты использовать оправданно, не создавать «микро-платформу» ради трёх домов.
- Код модульный, осмысленные компоненты, централизованные продуктовые данные/конфигурация, нет захардкоженных цен в нескольких местах.

## 3. Бренд и визуальная система

- Название: **«просто дача»**, только кириллица.
- Палитра: primary forest `#2D4938`, light ivory `#F5F2E9`, основной текст `#202820`, мягкие границы `#DCE2D9`; акценты только внутри гармоничной монохромной/нейтральной системы. **Лого строго монохромное**: зелёное на светлом / светлое на зелёном.
- Светлые поверхности, ровная осмысленная геометрия, ограниченный набор радиусов, аккуратные тонкие границы, редкие мягкие тени, достаточно воздуха.
- Кнопки, инпуты, табы, переключатели — предсказуемые, контрастные, без глубоких вложенных карточек и градиентного шума.
- Акцент на одном сильном изображении дома за раз. Строго сохранять пропорции архитектуры; не растягивать дом при адаптации под мобильный экран.
- Считать техническую ясность частью эстетики. Показывать реальные характеристики рядом с фото/планом, а не прятать их в гигантские аккордеоны.
- **Запрещено:** glassmorphism «ради стиля», бессодержательные анимации, бесконечные карусели, параллаксы, мигающие CTA, многоступенчатая навигация, карточки внутри карточек, тяжёлые hero-видео, обилие бейджей и декоративных иконок, длинные маркетинговые полотна.

## 4. Структура и маршруты

Сделай работающие страницы:
- `/` — основная маркетинговая страница из ~10 компактных смысловых секций по брифу.
- `/projects/[slug]` — карточка каждой из трёх моделей, отдельная полноценная responsive-страница (плотный и понятный первый экран).
- Уместные якоря в навигации; мобильное меню только если необходимо. Отдельные контакты и юридические страницы можно оформить минимально, но реальные документы/реквизиты не придумывать.

Проекты: `Дача 20` (4×5 м), `Дача 24` (4×6 м), `Дача 30` (5×6 м). **20/24/30 м² — площадь наружного прямоугольного контура, не автоматически полезная площадь.** Не присваивать им выдуманные утверждённые планы, стоимость, точную комплектацию или конструктивные параметры. Использовать типизированные поля `null`/`pending` и корректное UI-состояние «Стоимость уточняется» / «Планировка уточняется». Если есть терраса, её площадь показывать отдельно.

Секции главной:
1. Hero: суть, собственное производство, сезонные дома, два сценария: **комплект с доставкой** и **дом с монтажом**.
2. Сетка трёх проектов с фасадом, планом (если утверждён), размером, честной ценой (если утверждена), короткими CTA.
3. Комплектация: ясная граница «в комплекте / рассчитывается отдельно», из одной спецификации, никакого «под ключ» без состава.
4. Мини-брус и сезонность: сухой профилированный брус, фото узлов, честное предупреждение о сезонном использовании.
5. Собственное производство: доказательства (после предоставления контента) — материал, профилирование, маркировка, упаковка, ведомости.
6. Контекстный расчёт: **4 шага — формат → проект → населённый пункт и срок → один контакт**.
7. Доставка и монтаж: доставляем по выбранным направлениям Центральной и Южной России (по подтверждению); монтируем в Нижегородской области и ориентировочно до 500 км от Нижнего Новгорода после проверки маршрута. Не рисовать точную зону как гарантированную.
8. Пять этапов заказа: выбор → спецификация и смета → договор/производство → отгрузка → самостоятельная сборка или монтаж.
9. FAQ: 6 коротких вопросов из брифа.
10. Финальный CTA / собственный размер или эскиз; необязательная передача файла после первого контакта.

Отдельная **страница проекта** (главный UX-приоритет): на десктопе в первом видимом экране разместить крупный фасад/галерею, планировку/размеры, короткие характеристики, доступные опции и **короткую форму расчёта**. На мобильном — фото и название → размеры/сезонность → план → переключатель «комплект / монтаж» → CTA; длинную форму раскрывать в лёгком drawer/sheet или отдельной компактной секции. Не пытаться физически запихнуть всё на один мобильный экран; сохраняй последовательность чтения. Любой выбор проекта и опций передаётся в форму и сохраняется при переходах.

## 5. Формы и реальное поведение

- Основное действие: запросить расчёт выбранного дома с доставкой или монтажом.
- На каждой карточке есть действие «Рассчитать этот дом», которое предзаполняет правильные проект/формат в общей форме.
- Четыре небольших шага, осмысленный индикатор прогресса, доступна кнопка «Назад» без потери данных, минимум ручного ввода.
- Населённый пункт нужен для логистики. При выборе монтажа вне явной зоны не давать ложной гарантии; показать «Проверим доступность».
- Телефон **ИЛИ** Telegram, не оба сразу; имя необязательно. Согласие — отдельное, непредвыбранное; политика только с реальным URL после добавления документов.
- Реализовать внятные loading/empty/error/success states и предотвращение повторной отправки. Не имитировать успех отправки без реального backend/endpoint. Если backend ещё не подключён, покажи заметное «Демонстрационная форма — заявки не отправляются» и не обещай обратный звонок.
- Данные конфигурации и обезличенные события можно сохранять клиентски, **персональные данные в localStorage/analytics не сохранять**. UTM, проект, формат и шаги формы — интерфейсы для последующей аналитики, без «готовой» CRM, которой нет.
- Никаких искусственно низких цен. При отсутствии утверждённого прайса — прозрачное отсутствие цены с CTA на расчёт.

## 6. Mobile first — обязательные условия приёмки

Проверить 320, 360, 375, 390, 430, 768, 1024, 1440 и 1920 px:
- Без горизонтальной прокрутки, clipping, перекрытий и слишком мелких шрифтов.
- Целевые области нажатия не менее ~44×44 px, между ними разумные интервалы.
- Поля формы >=16 px для предотвращения autozoom в iOS Safari, верные `inputmode`, autocomplete и маски только там, где они помогают.
- Учесть safe-area-inset для fixed/sticky элементов и динамическую высоту viewport (`dvh`), избегать ловушек `100vh`.
- Фото и планы читаемы, не растянуты; план на мобильном увеличивается открытием/масштабированием.
- Стабильный layout при загрузке изображения и шрифта, нет CLS; hero корректно работает при увеличении текста в браузере.
- Видимая клавиатурная навигация, aria, семантика, контраст минимум WCAG AA для интерфейсного текста.
- Анимации не мешают, поддерживают `prefers-reduced-motion`, не блокируют взаимодействие, drawer можно закрыть Esc и жестом только если это не ухудшает доступность.
- Проверь на реальном эмуляторе/браузере, не просто по CSS.

## 7. Производительность

Референсные цели для тестового/production-билда при контролируемых условиях:
- LCP ≤ 1.5 s,
- TTFB ≤ 400 ms (лучше существенно ниже),
- Speed Index ≤ 2.0 s.
И дополнительно ориентиры: CLS ≤ 0.1, INP ≤ 200 ms. Измерять, а не гарантировать; приложить тесты, среду и найденные узкие места. Не грузить полноразмерные mockup PNG на hero в production; получить настоящие адаптивные assets. Использовать preload только для LCP-изображения и критических ресурсов; шрифты в разумном количестве. Не гидратировать весь лендинг.

## 9. Критерии успеха и запреты

Удачный сайт — тот, где за 5 секунд понятно: **мы производим дачные дома; можно выбрать 4×5 / 4×6 / 5×6; можно заказать комплект с доставкой или монтажом; можно получить расчёт на свой адрес.** На мобильном это должно быть ещё проще, а не «урезанная десктопная версия».

**Не надо:** усложнять поля и тексты; придумывать прайсы, сроки, отзывы, гарантии, статистику продаж и контакты; добавлять несвязанные категории; заявлять, что вся Россия покрыта доставкой/монтажом; рисовать фальшивые «реализованные проекты»; использовать AI-макеты как источник технических фактов; копировать CSS из старого концепта как финальную дизайн-систему; выдавать заявку за реально принятую без интеграции.

Начни с изучения папки пакета и наличия skills. Затем выполняй работу в текущем репозитории, показывая проверяемый результат и итоговый отчёт. Не ограничивайся рекомендациями или эскизом.
